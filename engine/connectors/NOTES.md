# Connector verification notes

All checks done 2026-10-14 by fetching the official pages listed. **Nothing here was live-tested**: no
credentials, stores or ad accounts were available. Tests use synthetic recorded-shape fixtures and
`httpx.MockTransport`. "Not verified" items are NOT implemented (or are flagged as secondary-source).

## Shopify (Admin GraphQL) - `shopify.py`
- Docs: https://shopify.dev/docs/api/admin-graphql/latest (+ `/queries/orders`, `/objects/Order`, `/objects/LineItem`, `/objects/Refund`, `/objects/RefundLineItem`, `/objects/OrderTransaction`, `/objects/MailingAddress`, `/objects/MoneyBag`), https://shopify.dev/docs/apps/build/apis/graphql-admin/rate-limits, https://shopify.dev/docs/api/usage/{rate-limits,access-scopes,versioning}, https://shopify.dev/docs/apps/launch/protected-customer-data, https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/offline-access-tokens
- Version: URL-versioned. Latest stable **2026-10** (supported to 2027-10-16); 2026-01/04/07 also supported. Default `2026-10`, configurable. Quarterly releases, >=12 months support.
- Endpoint: `POST https://{shop}.myshopify.com/admin/api/{version}/graphql.json`, header `X-Shopify-Access-Token`. HTTP 200 can carry `errors` (check body). 402/403/423 = shop frozen/fraud/locked.
- Scopes: `read_orders` (orders created in the **last 60 days only**), `read_all_orders` (full history; **needs Shopify approval**, declared with `read_orders`). Customer name/address/email/phone are *protected customer data* (Level 2: Partner Dashboard request + review for public apps; custom apps always available; unapproved fields return null / typed errors). `read_products`/`read_customers` not used.
- Query: `orders(first, after, query, sortKey, reverse, savedSearchId)` -> `OrderConnection` {`nodes`, `edges`, `pageInfo{hasNextPage,endCursor}`}. `query` filters verified: `created_at`, `updated_at`, `processed_at`, `financial_status` (syntax examples `updated_at:<now`, `created_at:'2020-10-21T23:39:20Z'`). The `>=` / `<` operators and the space-AND of two filters follow the generic search syntax and the `<=`/`<` examples; the combination was not shown verbatim (flag: confirm on first call).
- Fields used (all confirmed present on the pages above): Order `id name createdAt updatedAt processedAt cancelledAt displayFinancialStatus displayFulfillmentStatus currencyCode paymentGatewayNames tags sourceName email phone customer{id} subtotalPriceSet totalPriceSet totalDiscountsSet totalShippingPriceSet totalTaxSet totalRefundedSet shippingAddress transactions(first) lineItems(first) refunds(first)`; MailingAddress `city provinceCode zip countryCodeV2`; OrderTransaction `id kind status gateway processedAt amountSet`; LineItem `id name title sku quantity currentQuantity originalUnitPriceSet discountedUnitPriceSet totalDiscountSet`; Refund `id createdAt updatedAt note totalRefundedSet refundLineItems`; RefundLineItem `quantity restockType subtotalSet totalTaxSet lineItem`; MoneyBag `shopMoney{amount currencyCode}` (amount is a Decimal string; ledger converts to paise).
- Pagination: cursor (`after`/`endCursor`). Array pagination capped at **25,000 objects** -> backfill walks 30-day `created_at` windows; warning emitted if a window returns >=20,000. `lineItems` / `refundLineItems` nested connections are fetched at a fixed page size (default 15/10); if `hasNextPage` is true a warning is returned and `pageInfo` stays in the payload (no follow-up paging: the `order(id:)`/`node` query was not verified).
- Rate limits: calculated query cost, leaky bucket. Points/s: Standard 100, Advanced 200, Plus 1000, Enterprise 2000. Max single query cost 1000. Response `extensions.cost{requestedQueryCost, actualQueryCost, throttleStatus{maximumAvailable,currentlyAvailable,restoreRate}}`. Error `extensions.code`: `THROTTLED`, `ACCESS_DENIED`, `SHOP_INACTIVE`, `INTERNAL_SERVER_ERROR`, `MAX_COST_EXCEEDED`. Handling: proactive pacing from throttleStatus; on THROTTLED wait `(requestedQueryCost - currentlyAvailable)/restoreRate` (min 1 s, per docs' 1 s backoff advice) then retry with jittered exponential backoff.
- Auth flow: offline token (authorization-code grant for standalone apps, token exchange for embedded) at `POST https://{shop}.myshopify.com/admin/oauth/access_token`; admin-created custom apps can no longer be created. Public apps must use **expiring offline tokens (1 h + 90-day refresh token) by 2027-01-01**. The connector expects `{"access_token": ...}` in the encrypted credentials; the OAuth install flow and refresh-token flow are **NOT implemented** (refresh request parameters not verified). Needs a web/OAuth owner.
- NOT verified: `OrderSortKeys` enum values (not relied on: incremental sync filters with `updated_at` and tracks the watermark itself), numeric `first` maximum, `Retry-After` for GraphQL (honoured if sent, not relied on), per-plan bucket sizes (only an example of 1000), webhooks, bulk operations, `order(id:)`.
- PII decision: see DECISIONS.md. Requested identity fields: `email`, `phone`, `shippingAddress{city provinceCode zip countryCodeV2}`, `customer{id}`. Raw email/phone are hashed (sha256 of normalised value) and removed before persistence. Not requested: names, address1/2, shipping phone, payment details.

## Shiprocket - `shiprocket.py`
- Docs: official reference https://apidocs.shiprocket.in/ is JS-rendered and returned **no endpoint content** to the fetch tool. Verified from official helpsheet https://support.shiprocket.in/support/solutions/articles/43000337456-shiprocket-api-document-helpsheet and https://apidocs.shiprocket.in/view/metadata/SzYW1zB2 : base `https://apiv2.shiprocket.in/v1/external/`; `POST auth/login` with **API-user** credentials (a separate user, with an email not registered on Shiprocket, created under Settings > API); token valid **240 h**; `Authorization: Bearer <token>`; `GET courier/track/awb/{awb_code}`; documented HTTP codes include 401/422/429/5xx; webhook payload fields (`awb, courier_name, current_status, shipment_status, is_return, scans[...]`, optional `x-api-key` security header).
- Secondary-source (NOT verified in official text, flagged in code docstring): list path `GET shipments`, `page` param, response `{data:[...], meta:{pagination:{current_page,total_pages,total,per_page,links}}}` (from https://pkg.go.dev/github.com/Niyantra-Labs/shiprocket-gosdk/shipment), login response key `token`. Confirm on first real call.
- Rate limits: not documented anywhere reachable; 429 is a documented response code, so it is treated as retryable with jittered backoff (`Retry-After` honoured if present).
- Incremental: no verified server-side date filter -> each sync re-scans all pages (idempotent upsert). RTO/status vocabulary is not interpreted (raw kept; ledger decides). Tracking per AWB intentionally not called. Webhook receiver: out of scope (needs an API route owned by main).
- NOT verified: order list endpoint, filters (`from/to/sort/filter`), NDR endpoints (`ndr/all` seen in a third-party README only), status code vocabulary, rate limits.

## Meta Marketing API insights - `meta.py`
- Docs: https://developers.facebook.com/docs/marketing-api/reference/ad-account/insights/ , https://developers.facebook.com/docs/marketing-api/insights , https://developers.facebook.com/docs/graph-api/overview/rate-limiting , https://developers.facebook.com/docs/marketing-api/overview/rate-limiting , https://developers.facebook.com/docs/marketing-api/get-started/authorization , https://developers.facebook.com/docs/graph-api/guides/versioning
- Version: docs show **v26.0** as latest (versioning page) and v25.0 in insights examples; default `v26.0`, configurable. Marketing API has its own deprecation schedule (page not fetched).
- Endpoint: `GET https://graph.facebook.com/{version}/act_<AD_ACCOUNT_ID>/insights`. Params verified: `level` (ad|adset|campaign|account), `time_range{since,until}` (YYYY-MM-DD; sent JSON-encoded, Graph convention not shown verbatim), `time_increment` (1..90 / monthly / all_days), `fields`, `limit`, `date_preset` (`maximum` = up to **37 months**), `action_attribution_windows` (default `7d_click,1d_view` per reading section; docs inconsistent between sections - not overridden), `breakdowns`, `filtering`.
- Fields used: `date_start date_stop account_id account_currency campaign_id campaign_name adset_id ad_id spend impressions clicks reach actions action_values purchase_roas`. Values are strings, `spend` in account currency (ledger converts to paise; platform-reported ROAS is NOT causal).
- Pagination: Graph `paging.cursors.{before,after}`; we continue with `after` while `paging.next` is present (`next` key not shown on the fetched page: standard Graph behaviour, flagged).
- Rate limits: error codes 4 (app), 17 (user/ad account), 613 (custom), BUC 80000 (Ads Insights) / 80003 / 80004 / 80014 etc. -> retryable `RateLimitError`; headers `X-FB-Ads-Insights-Throttle`, `X-Ad-Account-Usage`, `X-Business-Use-Case` / `X-App-Usage` exist but are **not parsed** (units of `estimated_time_to_regain_access` unverified); backoff is jittered exponential.
- Auth / approvals: permission `ads_read` (OAuth `scope=ads_read`); Standard access is automatic for Business apps; **Advanced access (managing other people's ad accounts) requires App Review**, and sensitive access needs **Business Verification**; keeping Advanced access requires >=500 API calls / 15 days with <15% errors. Token: connector expects `{"access_token"}`; system-user/long-lived token mechanics and expiry were **not verified** (page did not cover) - the OAuth flow is NOT implemented.
- Dedupe key: `{level}:{account_id}:{object_id}:{date_start}`; trailing 14-day re-pull (`overlap`) since conversions are revised.
- NOT verified: token-expiry error code, async report jobs (large accounts), unified-attribution settings, breakdown combinations.

## Google Ads API - `google_ads.py`
- Docs: https://developers.google.com/google-ads/api/rest/auth , /rest/common/search , /docs/query/grammar , /docs/query/date-ranges , /docs/best-practices/rate-limits , /docs/api-policy/access-levels
- Version: **v25** (used in official REST examples; v26 mentioned in an event note). Default `v25`, configurable.
- Auth: OAuth 2.0 scope `https://www.googleapis.com/auth/adwords`; refresh `POST https://www.googleapis.com/oauth2/v3/token` (`grant_type=refresh_token, client_id, client_secret, refresh_token`); headers `Authorization: Bearer`, `developer-token` (every call), `login-customer-id` (manager-account calls; digits only).
- Endpoint: `POST https://googleads.googleapis.com/v25/customers/{customer_id}/googleAds:search`, body `{query, pageToken}`; response `results`, `nextPageToken` (10,000-row pages), JSON keys lowerCamelCase (`costMicros`, `segments.date`). `searchStream` is not used.
- GAQL: `SELECT campaign.id, campaign.name, segments.date, metrics.impressions, metrics.clicks, metrics.cost_micros FROM campaign WHERE segments.date BETWEEN 'YYYY-MM-DD' AND 'YYYY-MM-DD'` (BETWEEN verified on date-ranges page; dates evaluated in the **account time zone**; daily segments lookback **37 months**). Backfill walks 90-day windows.
- Rate limits: QPS token bucket per customer id and per Cloud project; over-limit -> `RESOURCE_TEMPORARILY_EXHAUSTED` (no retry delay documented -> jittered backoff). Daily operations by access level: Test 15,000; Explorer 2,880 production/day; Basic 15,000; Standard unlimited (sliding 24 h).
- Approvals: Google Cloud project + Google Ads API enabled, **developer token** (from a manager account), access level Explorer -> Basic (brand verification) -> Standard (manual audit, ~10 business days listed for Standard; others not stated).
- NOT verified (so not selected by default): `metrics.conversions`, `metrics.conversions_value`, `customer.currency_code`, `customer.time_zone` as selectable fields on the fetched reference pages (the field-reference pages were too large/truncated); pass `extra_metrics=[...]` explicitly after checking. Meaning of `cost_micros` (millionths of the account currency) was not found on a fetched page; the raw value is stored untouched and the ledger must confirm. Error-body shape for non-rate-limit errors, MCC child-account enumeration (`listAccessibleCustomers` seen in the example only) not implemented.

## CSV import - `csv_import.py`
- No official source; the engine is generic and has **no marketplace presets**. Samples needed from the user (real, anonymised exports) before any format support is claimed: Amazon Seller Central (order report + settlement/payments report), Flipkart (orders + settlement/payment report), Blinkit, Zepto, Swiggy Instamart (sales/PO + payout/invoice reports), each with: file name, date range, a few rows incl. a return/cancellation, a row with fees/deductions, the date format and timezone used, and whether amounts are tax-inclusive.
- Behaviour: UTF-8 (BOM ok), RFC4180 quoting, >25 MB or >200k rows rejected, duplicate headers rejected; money parsed from `1,299.50` / `Rs. 499` / `(10.00)` to integer paise (sub-paise precision rejected, never rounded); dates require explicit `formats` (never guessed), naive datetimes assumed IST unless `tz: UTC`, stored as UTC ISO.
